# 效率与工具链评估 — 用 gantry vs 不用 gantry

> 关联:[`DIAGNOSIS.md`](./DIAGNOSIS.md) · 基于同一 change 的实测数据 · 分析日期 2026-08-06

本评估回答一个问题:**同样这个需求,用 gantry 走完 vs 直接对话式开发,效率和工具链各是什么代价与收益?**
原则:开销和价值都摊开,并区分「gantry 造成的成本」与「需求本身不确定造成的成本」——两者常被混为一谈。

---

## 一、实测数据锚点(本 change)

| 项 | 实测值 | 性质 |
|---|---|---|
| 流程工件总量 | **246 KB**(PATCH 41KB / TASKS 67KB / DESIGN 28KB / REVIEW 33KB / …) | gantry 开销 |
| 原子任务 | 27 个(T01→T24+),各含 verify + evidence | gantry 开销 |
| Context 压缩 | 43 次 | 混合(见下) |
| 编排层工具调用 | TaskCreate/Update **82** · Agent(子代理)**14** · Skill 触发 ~20 | gantry 开销 |
| 底层工具调用 | Bash **358** · Read **270** · Edit **192** · Write **27** | 两种模式都需要 |
| 时间跨度 | 2.5 个工作日 | 混合 |
| 抓到的资损级缺陷 | **1**(T19,review 阶段) | gantry 价值 |

关键比例:**流程工件(246KB)/ 实际代码改动**明显倒挂。单个代表性提交量级是「8 文件 / 20 insert / 323 delete」(PATCH-4 记录),
即**围绕代码写的流程文字,数倍于代码本身**。这是 gantry 的固有开销,在此 case 被需求反复进一步放大。

---

## 二、成本对比(gantry 引入的额外开销)

| 维度 | 用 gantry | 不用 gantry(直接对话式) |
|---|---|---|
| **上下文开销** | 每次压缩后需从工件 + summary 重建;工件本身占大量 token | 只需对话历史,压缩更少但恢复质量低 |
| **仪式开销** | 每 task 写 verify/evidence/summary,每决策记 AC/ADR/PATCH | 无,直接改代码跑测试 |
| **记账开销** | 7 个 PATCH 的 supersedes / drop reason / 阶段回退全程手写 | 无,改了就改了(但也无痕迹) |
| **编排开销** | 82 次 Task 工具 + 14 子代理 + skill 状态机切换 | 主体直接干,几乎无编排层 |
| **启动摩擦** | change→requirement→design→…8 阶段门禁 | 零启动,想到就写 |

**小结**:gantry 在「前期结构化 + 全程记账」上有显著固定成本。对**简单/确定**需求,这个成本占比很高,收益薄。

---

## 三、收益对比(gantry 带来、对话式易缺失的东西)

| 维度 | 用 gantry | 不用 gantry |
|---|---|---|
| **资损防线** | T19 批 commit/rollback 假绿被 review 独立复核抓住 → 未上线 | 极可能全绿直接上线 → **用户持续扣款且永不解约** |
| **存量权益约束** | grandfather 老会员被钉进 AC,resolve/续费不 re-resolve 有专项测试 | 靠开发者记忆,易在改价时误伤存量 |
| **决策可追溯** | 机制①↔②的废弃/恢复/再删,PATCH.md 有完整理由链 | 无记录,3 个月后无人能解释为何这么设计 |
| **验收对齐** | 每改动映射到 AC,验收有据 | 验收靠口头/记忆 |
| **交接成本** | 新人读工件即可接手 | 需原作者口述 |

**小结**:gantry 的价值在**高风险 + 需长期维护 + 需审计**的场景兑现。本 case 恰好是资损敏感的支付域,T19 这一个被拦截的缺陷,其避免的损失可能已覆盖全部流程开销。

---

## 四、工具链对比

| 层 | 用 gantry | 不用 gantry |
|---|---|---|
| **编排层** | gantry skills(change/next/auto/adjust/review)+ 状态机 STATE.md + config | 无,或轻量 TODO |
| **任务层** | TaskCreate/Update(82 次)+ Wave 并行 + 子代理(14 次)分派审查/映射 | 主 agent 线性推进 |
| **验证层** | 每 task verify 命令 + evidence 留档 + 独立 reviewer 回环 | 手动跑 pytest,结果不留档 |
| **知识层** | LESSONS.md(L-002 假绿教训)+ PATCH.md 决策库 | 无沉淀,教训随会话消失 |
| **底层工具** | Bash/Read/Edit/Write(两模式一致) | 同 |

工具链差异的本质:gantry 在底层工具之上叠了**编排 + 验证 + 知识**三层。
这三层是它开销的来源,也是它价值的来源——**用不用它,取决于这三层对当前需求值不值。**

---

## 五、效率的诚实归因:哪些成本是 gantry 的,哪些不是

这是本评估最重要的判断,避免误把「需求锅」甩给「框架锅」:

| 成本 | 归因 | 说明 |
|---|---|---|
| 43 次压缩里的**大部分** | ❌ **不是 gantry 的** | 需求边设计边收敛(12 轮澄清)+ 机制反复,决策没沉淀到工件。换任何模式,这种不确定性都会烧上下文。gantry 的错在**没提供决策即沉淀的机制**(见 P0-1),而非制造了不确定性。 |
| 43 次压缩里**因工件臃肿**的部分 | ✅ 是 gantry 的 | 246KB 工件每次重载都吃 token,放大了压缩频率。 |
| 7 个 PATCH | ⚠️ 一半一半 | 设计反复是需求锅;但「只能塞进一个 change」是 gantry 缺 change 拆分机制的锅(P1-5)。 |
| 仪式/记账时间 | ✅ 是 gantry 的 | 固定成本,确定性需求上性价比低。 |
| T19 被拦截 | ✅ gantry 的正收益 | 对话式几乎必漏。 |

**结论性判断**:
- 在**这个 case**(支付域 / 资损敏感 / 需求高度不确定),gantry 的开销比被需求不确定性放大到接近临界,但**因为拦下 T19,净值仍为正**。
- 若同样需求**用对话式**:大概率快 1-2 天完成,但**T19 上线**的期望损失远超省下的时间。
- gantry 的**开销放大**主要来自两个可修的缺陷(决策未沉淀 P0-1、缺 change 拆分 P1-5),**不是框架的必然代价**。修掉后,同类 case 的开销比可显著下降。

---

## 六、决策指引:什么时候用 gantry

| 场景 | 建议 | 理由 |
|---|---|---|
| 资损/安全/合规敏感 | ✅ 用 | 验证层 + 独立 review 的价值兑现(T19 即证) |
| 需长期维护 / 多人交接 | ✅ 用 | 工件即交接物 |
| 需求高度不确定、边做边定 | ⚠️ 用,但先收敛设计再进 auto | 否则开销被放大(本 case 教训),配合 P0-1/P2-9 |
| 简单确定的小改动 | ❌ 直接对话式或 light 管线 | 固定开销占比过高 |
| 探索性/一次性脚本 | ❌ 不用 | 无维护、无审计需求,纯开销 |

---

## 七、给框架的量化改进目标

这些数字应成为 [`IMPROVEMENT-PLAN.md`](./IMPROVEMENT-PLAN.md) 落地后的验收基线:

- 同规模长 change 的**压缩次数**:从 43 降到 < 15(P0-1 决策沉淀 + P0-2 受控清窗)。
- **工件/代码体积比**:引入工件精简 / 归档裁剪,目标压到当前的 1/2 以下。
- **单 change PATCH 数**:靠 change 拆分(P1-5)回落到 ≤ 3。
- **资损级缺陷拦截率**:保持 100%(P1-7/P1-8 固化,不靠偶然)。
